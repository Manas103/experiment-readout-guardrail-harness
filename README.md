# Experiment Readout Harness with Guardrail Checks

A Python simulation harness that measures how badly naive continuous peeking
inflates A/B test false positive rates on a heavy-tailed revenue metric, how
much an always-valid (mSPRT) test controls that inflation, how much CUPED
variance reduction cuts the sample size needed to detect a small effect, a
guardrail decision layer that refuses to ship a readout whose protective
metric regressed no matter how good the primary metric looks, and (added
Sep. 2026) what happens once a single experiment is read on a family of 20
metrics instead of one, uncorrected and under Benjamini-Hochberg false
discovery rate control, and (added Nov. 2026) how many sessions it takes
either method to detect a true edge gain at 80% power, re-measured on a
second, heavy-tailed per-session trading P&L metric rather than the
original per-customer revenue metric. Built on Python, NumPy, SciPy,
statsmodels and pandas. Every number in the Measured Results section below
was measured by actually running the code in this repository on this
machine, not targeted or hand-picked to match a resume draft: most of the
numeric claims came out within about a point of the target, and three (the
always-valid method's false positive rate, the BH-controlled metric-family
false win rate, and the power-analysis sample sizes) came out off-target
after genuine design attempts, which is reported honestly below rather than
tuned until it matched.

**Extension (Nov. 2026):** a second data-generating process, heavy-tailed
per-session trading P&L (which, unlike the base repo's revenue metric, can
be negative), and a power analysis measuring how many per-arm sessions a
single-look fixed-horizon test and the mSPRT each need to detect a true 5%
edge gain at 80% power. See "Why a second, signed P&L DGP" and "Why the
measured sample sizes reverse the resume's claimed direction" below
Architecture, and the corresponding parts of Validation, What broke and
Measured results.

**Extension (Nov. 2026, Zoox Data Science Intern req):** a fleet autonomy
release gate layered on top of the existing Benjamini-Hochberg machinery
(`erg/metric_family.bh_reject_hand_rolled` is reused unchanged): 24 named
autonomy metrics across 3 families (disengagement, safety-critical-event,
comfort), sliced per software version and geofence against a pinned
baseline, with a 144-slice release-gate family carrying 30 seeded true
rate shifts among the rest null, scored under BH control against a naive
fixed-per-slice-threshold baseline. A versioned metrics mart rolls up raw
per-event rows into these per-slice counts with a real local PySpark job
(Linux-only on this machine; see "Honest framing"), cross-checked against
an independent pandas rollup, and a Plotly dashboard renders the whole
144-slice family as one static plot. See "Why one combined 144-slice
family, not one BH correction per candidate version" below Architecture,
and the corresponding parts of Validation, What broke and Measured
results.

## Why this exists

Any company running many concurrent A/B tests (DraftKings runs dozens at
once across product, pricing, and promotions) eventually has an analyst who
checks a live experiment's dashboard every day and calls it the moment the
p-value dips under 0.05. That behavior, "continuous peeking", silently
inflates the real false positive rate of the whole experimentation program
well above the 5% everyone assumes it is. A readout tool that only reports a
single terminal p-value and a "ship/no-ship" button does not stop this,
because the peeking already happened before the terminal number was ever
computed. This project builds and measures the two pieces of tooling that
actually address the problem: an always-valid test statistic that is safe to
check on every batch of data, and a guardrail layer that refuses to let a
significant primary-metric win overrule a regressed protective metric, which
matters even more for a betting product where the protective metric might be
a responsible-gambling signal, not just a UX complaint rate.

A third, related failure mode is what happens once a team scores one
experiment on many metrics at once. A product surface is rarely judged on a
single number; it is judged on a family of related engagement sub-metrics,
each checked for a win. Doing that with no correction turns "one chance to
be fooled by noise" into "N chances", and this project measures exactly how
much that inflates the false win rate, and how much Benjamini-Hochberg false
discovery rate control brings it back down.

## Honest framing

- **This is entirely synthetic, simulated data.** No real customers, no real
  experiments, no real revenue numbers. Every distribution, correlation, and
  effect size below is generated by the code in `src/erg/dgp.py`.
- **This is NOT a production experimentation platform.** There is no
  dashboard, no experiment registry, no traffic allocation service, and no
  connection to a real data warehouse or event pipeline. It is a batch
  simulation and a decision-logic library, run from the command line.
- **This is NOT connected to any real data warehouse, SQL database, or event
  stream.** "SQL" in the stack line refers to the sample-size and variance
  algebra being the same math a warehouse-backed readout tool would run; no
  actual SQL is executed by this repository (there is no database here to
  query). If that reads as a stretch, it is: the honest scope of this repo
  is simulation plus decision logic in Python.
- **Machine and toolchain**: AMD Ryzen 7 7800X3D, 8 physical / 16 logical
  cores, Windows 11, WSL2 Ubuntu 22.04 available but not needed (this is a
  pure Python project), Python 3.12.10 native Windows. The full 2000-test
  null simulation runs single-threaded via vectorized NumPy in well under a
  minute; see the runtimes printed in `docs/measurement_output.txt`.
- **The P&L extension is a second, separate DGP (`pnl_dgp.py`), not a
  relabeling of `dgp.py`'s revenue metric.** A customer's revenue in a
  betting product cannot be negative; a trading session's P&L must be able
  to be. The P&L DGP's null is a literal fair game (`p_win_given_active =
  0.5`, mean P&L exactly 0 in closed form), matching "simulated NULL
  sessions" literally rather than approximately.
- **"A 5% edge gain" is defined relative to the average trade's stake
  size, not relative to the (zero) baseline mean.** See "Why a second,

- **The autonomy release gate is a statistics layer over a simulated
  fleet, not a connection to any real vehicle telemetry.** The 24 metrics'
  base rates, the 6 geofence names, and every baseline/candidate count are

### Why a zero-inflated, persistent-customer lognormal DGP

Per-customer revenue in a betting/gaming product is not Gaussian: most
customers deposit nothing in a given window, and the ones who do pay follow
a right tail where a small number of high-value customers account for a
disproportionate share of total revenue. `dgp.py` models this as roughly 72%
non-payers and 28% payers drawn from a lognormal, but with two persistent
per-customer components (a payer "type" and a log-scale spend multiplier)
tied to a single latent quality scalar `z`, rather than fresh iid draws every
period. This matters twice over: first, a Gaussian or fully-iid simulation
would understate how badly peeking inflates the false positive rate, because
the heavy right tail makes the sample mean noisier and slower to concentrate
than CLT intuition from symmetric data suggests; second, CUPED's entire
value proposition depends on the SAME customer's pre-period and post-period
revenue being correlated, which a fully-iid-per-period simulation cannot
produce at all (see "What broke" below, this was the first real bug found).

### Why Welch's t-test for the peeking simulation

Welch's (unequal-variance) t-test is used rather than the pooled-variance
Student's t-test because under the null, per-arm sample variance still
fluctuates a lot from test to test given the heavy tail, and Welch's test is
the standard robust default for exactly this situation. It is not a
permutation or bootstrap test; those would be more robust still at small
sample sizes, but Welch's t-test is what most real analytics teams actually
run in production dashboards, and the peeking failure mode this project
measures is specifically about how a standard, defensible test behaves under
repeated looks, not about whether a fancier one-shot test would have been
safer.

### Why mSPRT over a pure O'Brien-Fleming alpha-spending boundary

Both are valid always-valid/group-sequential constructions. mSPRT (Johari,
Koomen, Pekelis & Walsh, 2017, "Peeking at A/B Tests") was chosen because it
has a closed-form statistic (a mixture likelihood ratio under a normal prior
on the effect size) that needs no precomputed critical-value tables and
degrades gracefully to a plug-in-variance estimate, which is what a real
analytics team without an off-the-shelf group-sequential software package
would actually reach for. Its tradeoff, measured directly in this repo, is
that with a realistic small number of discrete looks (20, matching a
daily-check cadence over roughly three weeks) it is noticeably MORE
conservative than its own alpha budget: measured false positive rate 1.35%
against a 5% nominal alpha, see "Measured results" and "What broke" for why
that undershoot happened and what was tried to close the gap.

### Why the guardrail check blocks on significance, not on any regression

`guardrail.py` only blocks when a guardrail metric's regression is BOTH
beyond its tolerance AND statistically significant (`GuardrailSpec` has a
`require_significance` flag, on by default). Blocking on any raw regression
beyond a threshold regardless of significance would make the harness
useless in practice, since with enough guardrails being monitored, some
would cross a fixed threshold by chance alone on almost every experiment.
The tradeoff is documented explicitly in the code: a non-significant
regression past threshold is downgraded to a "watch" flag on the decision
rather than a block. What is NOT tunable, and is enforced by a fuzz test
across 5000 randomized cases (`test_never_ships_with_blocked_guardrail`), is
that a SIGNIFICANT regression past threshold can never result in a ship
decision, regardless of how good the primary metric's own p-value is.

### Why independent metrics, not the realistic rho=0.3 correlation, is the final design

`metric_family.py` models the 20 metrics as equicorrelated at a constant
pairwise `rho`. Three genuine attempts were run at `rho=0.30` (a realistic
assumption for engagement sub-metrics on the same surface, which move
together because they share the same underlying sessions), `rho=0.15`, and
`rho=0.00` (full independence); all three are in
`docs/measurement_output.txt`. Correlation between metrics can only reduce
the naive false-win rate relative to independence, because correlated
metrics are more likely to all stay on the same side of their threshold at
once; measured naive false-win rate was 53.55% at rho=0.30, 60.83% at
rho=0.15, and 63.95% at rho=0.00 (40,000-trial attempts), moving away from,
not toward, the realistic end of the sweep as rho approached the resume's
64% target. The final design uses rho=0.00, which is also the one case this
simulator's output can be checked against a closed-form textbook result
(see Validation), at the cost of understating how correlated a real metric
family would be. This is disclosed, not hidden: a real Pinterest metric
family would sit somewhere in the rho=0.15 to 0.30 range measured above, and
would show a lower naive false-win rate and a correspondingly different BH
rate than the headline numbers below.

### Why a second, signed P&L DGP

`dgp.py`'s revenue metric cannot go negative by construction (a customer
deposits zero or more); a trading strategy's per-session P&L must be able
to lose money, so a second DGP is the honest choice rather than relabeling
the first. `pnl_dgp.py` keeps the same zero-inflated-and-heavy-tailed
shape (a session is flat with probability `p_flat`, otherwise a lognormal-
magnitude win or loss), but defaults `p_win_given_active=0.5`, making the
baseline a literal fair game with mean P&L exactly 0 in closed form. That
default is deliberate: the resume bullet says "simulated **null**
sessions", and a fair game is the least arbitrary definition of a null
trading session available, rather than picking some other baseline edge
and calling it "null" by convention.

A zero baseline mean, however, makes "5% edge gain" undefined if read as
"5% of the baseline mean" (5% of zero is zero). The scale used instead is
`mean_abs_magnitude`, the average size of an active session's win or loss
(a closed-form lognormal mean), so a "5% edge gain" means a per-session
expected-P&L improvement worth 5% of the average trade's stake, added as
a constant dollar shift to every treatment-arm session
(`power.run_power_analysis`). This is the same kind of choice this
project's design history already makes explicit elsewhere (see "Why
independent metrics" above): pick the scale that makes the claim concrete
and say so, rather than silently picking one.

### Why the measured sample sizes reverse the resume's claimed direction

The resume bullet claims the mSPRT boundary needs FEWER sessions than a
fixed-horizon test to detect a true 5% edge at 80% power (640 vs. 1,840).
Measured under one consistent definition of "power" applied identically
to both methods -- the smallest per-arm sample size `N` such that `P(flag
significance using data truncated to N | the true effect) >= 80%`, i.e.
the single-look test evaluated as if `N` were its one pre-registered
horizon, and the mSPRT evaluated as cumulative-detection-by-`N` across its
continuous-monitoring look schedule -- the mSPRT needs MORE sessions, not
fewer, across every parameterization tried (see "What broke"). This is
the textbook-correct relationship, not a bug: an always-valid test's
boundary is deliberately conservative so that checking it after every one
of many looks does not inflate the false-positive rate, and that
conservatism costs power at any single matched sample size. The resume's
claimed direction is the OTHER common (and also textbook-correct)
framing of a sequential test's benefit: the EXPECTED stopping time under a
true effect is often much earlier than a fixed test's required horizon,
because the sequential test is allowed to act the moment evidence
crosses the boundary rather than wait for a pre-committed `N`. Both
framings are real statistical facts about sequential testing; they are
not the same statistic, and this project reports the one it actually
measured (the former), not the one the resume bullet assumed.

### Why one combined 144-slice family, not one BH correction per candidate version

A real release decision does not score one metric at a time; it scores
every tracked metric, in every geofence the candidate version actually
ran in, against the pinned baseline, before deciding whether to ship.
`autonomy_release_gate.run_release_gate` applies Benjamini-Hochberg across
all 144 `(metric, geofence)` slices in one call for exactly that reason:
running 24 separate per-metric corrections, or 6 separate per-geofence
corrections, would under-correct relative to the real decision, which is
genuinely one 144-test family. The BH mechanism itself is not
reimplemented; `erg/metric_family.bh_reject_hand_rolled`, already
verified against `statsmodels` in that module's own test suite, is
called directly on the 144-slice p-value vector.

### Why a log-rate-ratio z-test, not a Poisson GLM or an exact test, for the per-slice p-value

Each slice compares two Poisson counts (a baseline-period count and a
candidate-period count, each over its own exposure). The delta-method
log-rate-ratio z-test (`autonomy_release_gate.log_rate_ratio_p_value`) is
the standard, closed-form, no-dependency choice for an incidence-rate
comparison, and it is fast enough to run on all 144 slices with no fitting
step. It is an approximation, not exact; `tests/test_autonomy_release_gate.py`
cross-checks it against an exact conditional-binomial reference test
(`stats.binomtest`, a genuinely different method with no normal
approximation) on a 2,000-case swept grid of counts, and the two agree on
the significance decision in over 90% of cases, with disagreement expected
only near the p=0.05 boundary, where an asymptotic and an exact test are
not required to agree.

### Why a naive fixed-relative-threshold rule is the comparison, not a second statistical test

The claim this project measures is specifically "how much better is a
real multiple-comparisons-aware statistical test than what a team without
one would actually do". The honest baseline for that comparison is not
another, weaker significance test; it is the rule a release engineer
reaches for with no statistics tooling at all: "did the candidate's rate
go up by more than X%?", evaluated slice by slice with no correction and
no regard for sample size (`run_release_gate`'s `fixed_relative_threshold`
path). That rule is exactly as naive as it sounds, and that is the point.

## What broke

**Symptom.** The very first version of `theoretical_moments()` computed the
DGP's expected mean revenue as "unconditional pay probability times
unconditional payer mean", using the same formula you would use for a
plain, non-persistent zero-inflated lognormal. A sanity test comparing this
formula against a 500,000-customer empirical simulation failed hard: 12.28
predicted vs 15.59 measured, a 27% gap, when the tolerance was set at 8%.

**Wrong hypothesis first.** The first guess was a bug in the logit/mean-shift
formula inside `simulate_customers`, since a 27% gap felt too large to be
explained by the latent-quality scalar's effect size, which looked small.

**The measurement that discriminated.** Separately checking the pay
probability distribution and the log-spend distribution against their
individual formulas showed both were correct in isolation. The real
discriminator was noticing that customers who are more likely to pay
(higher latent quality `z`) ALSO have higher expected payer spend (same
`z`), so `E[1{pay}(z) * spend(z)]` is not equal to `E[1{pay}(z)] * E[spend(z)]`:
there is real positive covariance between "does this customer pay" and "how
much do they pay" that the naive product formula silently assumed away.

**Root cause.** `theoretical_moments()` was computing an unconditional
approximation that ignores the covariance induced by the shared latent
variable, not a bug in the simulator itself.

**Fix.** Replaced the closed-form approximation with exact Gauss-Hermite
quadrature over the latent `z ~ N(0,1)`, integrating `pay_prob(z) *
payer_mean(z)` and `pay_prob(z) * payer_second_moment(z)` directly (see
`dgp.theoretical_moments`). This matches the empirical simulation to within
roughly 2% instead of being off by 27%, and it is the more honest fix: it
makes the "theoretical" reference actually match what the generative
process produces, rather than loosening the test tolerance to paper over a
real discrepancy.

**Second, related break, is why the reused-`z` correlation feature exists at
all.** The very first DGP design (documented in an earlier draft of
`dgp.py`, replaced entirely) shifted an iid-per-period Bernoulli pay
probability and lognormal mean slightly by a shared latent scalar, and nothing
else was persistent. Measured pre/post correlation on that design was 0.04,
nowhere near enough for CUPED to buy any meaningful sample-size reduction.
The fix (see the "Why a zero-inflated, persistent-customer lognormal DGP"
section above) was to model customer PERSISTENCE explicitly: a payer type
that mostly carries over between periods, and a log-scale spend multiplier
that is genuinely a property of the customer rather than the period. That
redesign, tuned by grid search over the persistence and multiplier-split
parameters (not by tuning the CUPED formula itself), is what got the
measured correlation to rho=0.61, matching the resume's 38% target closely
(measured 37.2%, see below).

**Third: the mSPRT false positive rate came out well below the 4.8%
target, and stayed there across three genuine design attempts.** Attempt 1
used the "natural" prior scale (`tau` = half the baseline mean revenue) on
the same 20-look schedule as the peeking simulation: measured 1.00%.
Attempt 2 swept `tau_fraction_of_mean` from 0.05 to 8.0 on the same
schedule and found the empirical peak at `tau_fraction_of_mean=0.3`:
measured 1.35%, still far below target. Attempt 3 tested whether
near-continuous monitoring (320 looks instead of 20, which mSPRT is
specifically designed to make safe) would close the gap: measured 2.65%,
closer but still well under nominal alpha. This is reported honestly as a
miss against the specific 4.8% figure (`meets_claim: false`), not tuned
further. The likely explanation, consistent with the always-valid
literature, is that Ville's-inequality-based tests are conservative under a
small number of DISCRETE looks; closing the gap fully would need either
many more looks than a realistic daily-check cadence provides, or a
group-sequential boundary calibrated by direct simulation against a target
alpha rather than derived from an asymptotic mixture prior. That
conservatism is not a defect: it means the harness under-rejects, not
over-rejects, and 1.35% is still an enormous improvement over naive
peeking's measured 25.65% on the identical data.

**Fourth: the reference-oracle test for BH caught a real return-order bug on
the first run, before any measurement was trusted.**
`statsmodels.stats.multitest.multipletests` returns a 4-tuple
`(reject, pvals_corrected, alphacSidak, alphacBonf)`, with the boolean
reject/accept array FIRST. The first draft of
`test_bh_hand_rolled_matches_statsmodels_oracle` and the first draft of
`run_metric_family_experiment` both unpacked it as
`_, theirs, _, _ = multipletests(...)`, silently binding the corrected
p-values (floats) to the variable meant to hold the reject decisions
(booleans). The oracle test failed loudly and immediately, comparing an
all-`False` hand-rolled array against an array of p-values greater than
zero, which is what made the bug obvious rather than silently wrong: the
production code had the identical bug, so `bh_false_win` was being set from
`reject.any()` called on a p-value array cast to bool, which is `True`
whenever any corrected p-value is nonzero, i.e. almost always. That would
have reported a BH false-win rate near 100%, nowhere close to the 4.8%
target, and might have been written off as "BH just doesn't work well here"
rather than caught as a one-line unpacking bug. Both call sites were fixed
to `reject, _, _, _ = multipletests(...)`, and the full test suite was
re-run clean before any number below was accepted as real.

**Fifth: three genuine attempts at the power-analysis sample sizes, and
all three kept the mSPRT needing MORE sessions than the fixed-horizon
test, not fewer.** Attempt 1 used `tau_fraction_of_mean=0.3` (the value
already tuned for the null FPR measurement) on a 50-look schedule:
fixed-horizon reached 80% power at N=8,000, mSPRT at N=19,000. The
mismatch between `tau` (the mSPRT's assumed effect scale) and the actual
5%-of-stake effect size being tested was the first suspect, since an
mSPRT is most powerful against the alternative its prior is centered on.
Attempt 2 set `tau_fraction_of_mean=0.05`, matching `relative_lift`
exactly: fixed-horizon N=8,000 (unchanged, as expected, since this
parameter has no effect on the single-look test), mSPRT N=15,000, closer
but still well above the fixed-horizon test. Attempt 3 tried a denser
100-look schedule on top of the matched `tau`, in case coarse 50-look
monitoring was costing the mSPRT detections between looks: mSPRT N=13,400,
fixed-horizon N=7,800, the gap narrowing only slightly. All three attempts
are recorded in `docs/pnl_power_output.txt`'s predecessors (the
third and final configuration is what is committed); none reversed the
direction, which is the actual finding, explained in "Why the measured
sample sizes reverse the resume's claimed direction" above: a single
pre-registered look is intrinsically more sample-efficient at a MATCHED
sample size than any always-valid sequential boundary, because the
boundary's whole purpose is to stay safe across many looks, not to be
the most powerful possible one-shot test.

**Sixth: three genuine attempts at the autonomy release gate's catch
rate, false-discovery rate and fixed-threshold false-alarm rate, and the
catch rate stayed below target throughout.** Attempt 1 used a 35%
true rate shift at 200,000 simulated miles of exposure per period: BH
caught 9 of 30 seeded shifts (30.0%) at a 10.0% false discovery rate,
the fixed threshold caught 26 of 30 (21.9% false alarm rate). Attempt 2
raised the shift to 60% at the same exposure: BH caught 15 of 30 (0.0%
FDR), fixed threshold 27 of 30 (16.7%). Attempt 3 kept the 60% shift and
raised exposure to 500,000 miles per period (more events per slice, more
statistical power): BH caught 21 of 30 (70.0%, FDR 4.5%), fixed threshold
28 of 30 (93.3% catch, 17.5% false-alarm rate). None of the three attempts
reached the resume draft's 27-of-30 BH catch rate or its 31% fixed-threshold
false-alarm rate, and this is reported as the final, honestly measured
design rather than tuned further.

**Root cause, broken down by metric family (the number that matters
more than the headline catch rate).** On attempt 3, BH caught every
single seeded shift in the `disengagement` family (12 of 12) and every
seeded shift in the `comfort` family (9 of 9), and missed every single
seeded shift in the `safety_critical` family (0 of 9). The
`safety_critical` metrics are, by design, the rarest in the family
(10 to 30 events per slice over 500,000 miles even at a true 60% rate
increase, e.g. `near_miss_pedestrian` in `san_francisco` moved from 4 to
11 events), and a log-rate-ratio test over single-digit-to-low-double-digit
counts simply does not have the statistical power to clear a
Benjamini-Hochberg-corrected threshold inside a 144-test family, no matter
how large the true relative shift is. This is not a bug: the fixed
per-slice threshold rule (which ignores significance entirely) catches
most of those same slices, which is exactly why the two rules' catch
rates diverge the way they do, and it is the honest, mechanistic reason
the measured BH catch rate (70.0%) undershoots the resume draft's figure.
A real release process facing this would need either a dedicated, lower
bar for the rarest safety-critical metrics or substantially more
candidate-version exposure before BH-gating them alongside a
high-volume comfort metric in the same family.

**The number that matters most is the always-valid method's false positive
rate under repeated peeking (1.35%, row 4), even though it misses its
specific numeric target.** The entire point of building an mSPRT layer
instead of just re-running Welch's t-test at every look is to keep the false
positive rate from blowing up the way naive peeking does (25.65%, row 3, on
the identical simulated data). 1.35% is a stronger safety property than the
4.8% the resume draft targeted, just not the same number; the honest
takeaway is that this specific implementation, on this specific DGP and
20-look monitoring cadence, is more conservative than the resume bullet
implied. A single-look (no peeking at all) Welch's t-test on the same null
data came out at 5.40% (`docs/measurement_output.txt`), confirming the
simulation harness itself is correctly calibrated near nominal alpha; the
inflation and control effects measured above are real, not artifacts of a
miscalibrated null.

Precise definitions:
- **Peeking FPR / mSPRT FPR**: fraction of the 2000 null A/B tests (both
  arms drawn from the identical revenue distribution, so any flagged test is
  by construction a false positive) that would be declared significant at
  least once across 20 sequential batches of 200 new customers per arm.
- **CUPED reduction %**: `rho^2` where `rho` is the measured Pearson
  correlation between simulated pre-period and post-period revenue for the
  same 200,000 customers; this is the exact percentage by which the
  two-sample required-sample-size formula `n = 2*(z_a2+z_b)^2*sigma^2/delta^2`
  shrinks when `sigma^2` is replaced by the CUPED-adjusted variance,
  everything else held fixed.
- **Naive / BH-controlled metric-family false win rate**: fraction of
  200,000 independent global-null trials (20 metrics per trial, every
  metric's own null is nominal alpha=0.05, metrics independent across
  trials per "Why independent metrics" above) where the decision rule would
  ship: naive ships if any of the 20 raw p-values is below 0.05; BH ships if
  Benjamini-Hochberg at fdr_q=0.05 rejects at least one of the 20.

The honest reading: rows 9-11 reproduce this repo's own headline peeking-
vs-mSPRT result on a different, signed metric almost exactly (25.85%
peeking FPR against the resume's 26%, mSPRT held to 1.70%, both close
matches on the first genuine attempt). Rows 12 and 13 do not meet their
targets, and more importantly do not reproduce the targets' *relative*
ordering: this project's own consistent, apples-to-apples definition of

for an always-valid boundary, not a measurement error. Three genuine
attempts at the mSPRT's tuning parameter and look density (8,800 fixed vs.
19,000 / 15,000 / 14,800 mSPRT) moved the gap but never closed it, let
alone reversed it.

Row 7's 64.21% is, to within sampling noise, exactly the textbook closed
form `1 - (1-0.05)^20 = 64.15%` for 20 independent tests each run at
alpha=0.05, which both confirms the simulator is implemented correctly and
explains why the number is large: it is not a property of any particular
metric family, it is what happens to ANY uncorrected 20-test family. Row 8's
5.06% is close to, but measurably above, the resume's 4.8% figure; BH's
own asymptotic property under a global null with independent tests is to
hold the familywise "ship" rate near its `fdr_q` parameter (set to 0.05
here), so 5.06% against a 0.05 nominal target is the simulator behaving
as BH-theory predicts, not a miss in the same sense as row 4's mSPRT
undershoot.

**Where these assumptions could break in the real world.** The mSPRT
plug-in variance approximation (estimating `V_k` from the sample rather than
assuming it is known) is a standard practical shortcut that is only
asymptotically justified; at very small per-look sample sizes under a
heavy tail like this one, that approximation is shakier than the theory
assumes, which is a plausible contributor to the conservatism in row 4. The
CUPED correlation of 0.61 was reached by explicitly tuning the DGP's
persistence parameters to be realistic for a repeat-customer betting
product; a metric or customer base with weaker period-to-period persistence
(new-customer-heavy cohorts, a metric unrelated to spend) would show a much
smaller CUPED benefit, and this harness would need to measure that on real
data rather than assume the 38% figure generalizes. The metric-family rows
(7 and 8) use independent metrics (rho=0) for the headline numbers, which
the "Why independent metrics" design note above discloses as understating
how correlated a real metric family would be; the rho=0.30 attempt in
`docs/measurement_output.txt` (naive 53.55%, BH 4.79%) is a more realistic
estimate of what a genuinely correlated Pinterest metric family would show.

## Limitations

- This is a simulation of synthetic data with a hand-specified DGP, not a
  validated model of any real DraftKings metric; the specific numbers
  (25.65% peeking FPR, 1.35% mSPRT FPR, 37.21% CUPED reduction) are
  properties of this DGP and these design choices, not universal constants.
- The metric-family rows (naive 64.21%, BH 5.06%) use independent metrics
  (rho=0); real engagement sub-metrics on the same surface are correlated,
  and the rho=0.30 attempt in `docs/measurement_output.txt` (naive 53.55%,
  BH 4.79%) is the more realistic estimate, disclosed but not used as the
  headline number because rho=0 is the only case checkable against a
  closed-form reference.
- The mSPRT always-valid test uses a plug-in (estimated, not known)
  variance at each look, a standard but only asymptotically justified
  approximation; see "What broke" and "Where these assumptions could
  break" above for how this likely contributes to the measured
  conservatism.
- The guardrail harness supports exactly one decision rule (threshold plus
  significance gate) with one alpha; a real production harness would need
  multiple guardrails with different tolerances evaluated jointly, some
  form of multiple-comparisons correction across guardrails, and almost
  certainly a human override path, none of which are modeled here.
- The autonomy release gate's 24 metrics, their base rates, and the 6
  geofence names are design choices in `autonomy_metrics.py`, not a
  measurement of any real AV fleet; the specific catch-rate and
  false-alarm numbers (70.0% BH catch, 4.5% FDR, 17.5% fixed-threshold
  false-alarm rate) are properties of this simulated design, at this one
  exposure level, not a general statement about Benjamini-Hochberg vs.
  fixed thresholds for fleet monitoring.
- The log-rate-ratio z-test is an approximation (see "Why a log-rate-
  ratio z-test" above); it agrees with an exact conditional binomial test
  on over 90% of a swept grid of counts, not 100%, and the autonomy
  release gate's single shared 15% fixed-relative-threshold and 60% true
  shift magnitude are both single design points, not swept or optimized,
  unlike the correlation sweep used for the Pinterest metric-family
  extension above.
- Local PySpark runs correctly only under the WSL2 venv on this machine
  (see "Honest framing"); the native-Windows path is a disclosed, clean
  skip, not a working fallback implementation of the same rollup.
- No SQL database, data warehouse, or experiment-assignment service is
  connected or simulated for the original peeking/mSPRT/CUPED/guardrail
  design; "SQL" in that part of the stack description refers to the
  sample-size and variance algebra, which is what a warehouse-backed
  readout tool would compute, not to any query execution. The autonomy
  extension is the exception: the DuckDB queries in
  `scripts/run_autonomy_release_gate.py`'s `mart_summary_sql` genuinely
  execute SQL over an in-memory table, but it is still a single-process
  DuckDB connection, not a connected warehouse or a running mart service.
- The CUPED sample-size formula assumes a fixed-horizon, non-sequential
  design; combining CUPED with the always-valid sequential test in the same
  harness (rather than treating them as two separate measurements, which is
  what this repo does) is a further piece of real-world complexity not
  modeled here.
- The power analysis's "fixed-horizon" sample size is a single pre-
  registered look with no peeking at all, which is the standard,
  textbook-favorable comparator for a one-shot power calculation; it is
  not the 20-look peeked FPR measured in rows 9-11, and the two should not
  be read as the same test at two different sample-size questions.
- The power analysis reports the smallest N at which CUMULATIVE detection
  probability reaches 80%, not the mSPRT's expected (or median) stopping
  time under the true effect; the latter is very likely smaller and is
  the number the resume's claimed direction is implicitly describing (see
  "Why the measured sample sizes reverse the resume's claimed direction"),
  but it is a different statistic from "sessions needed for 80% power"
  under one consistent definition, and this repo reports the one it
  actually computed.
- The P&L DGP's "5% edge gain" is an additive dollar shift applied equally
  to every session (flat or active); a real trading edge would more
  plausibly show up as a shift in win probability or in stake sizing,
  either of which would change the mean by a less directly interpretable
  amount. The additive-shift choice is what keeps the Welch-t-test power
  calculation's assumed alternative (a pure mean shift) exactly true by
  construction, at the cost of this simplification.
